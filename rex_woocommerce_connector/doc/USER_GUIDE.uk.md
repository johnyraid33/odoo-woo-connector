## 1. Що робить конектор

Модуль з'єднує одну базу Odoo з одним або кількома магазинами WooCommerce.
Магазин — це запис в Odoo (**WooCommerce > Магазини**); кожен інший об'єкт модуля
належить магазину, тому товар, клієнт або замовлення можуть синхронізуватися з
кількома магазинами незалежно.

| Напрямок | Об'єкт | Механізм |
| --- | --- | --- |
| WooCommerce → Odoo | Товари, варіанти, атрибути, ціни, зображення | Плановий опитувач (60 хвилин) і вебхуки `product.*` |
| Odoo → WooCommerce | Товари та їхнє основне зображення | Сервіс експорту, див. [розділ 10](#10-експорт-каталогу) |
| Odoo → WooCommerce | Залишки на складі | Планова дія (встановлюється **вимкненою**) і кнопка **Синхронізувати зараз** |
| WooCommerce → Odoo | Залишки як коригування запасів | Сервіс вивантаження, коли джерело запасів — WooCommerce |
| WooCommerce → Odoo | Замовлення, клієнти, повернення | Вебхуки `order.*` і `customer.*` та опитування замовлень кожні 10 хвилин; повернення надходить як зміна свого замовлення |
| Odoo → WooCommerce | Номери відстеження | Автоматично під час підтвердження вихідної доставки |

Конектор ніколи не звертається до WooCommerce під час відкриття сторінки: кожен
вихідний виклик — це завдання черги, тому повільний або недоступний магазин не
блокує інтерфейс Odoo.

## 2. Вимоги

* **Odoo** 19.0 або 20.0, Community чи Enterprise. Модуль залежить від
  стандартних модулів `sale_management`, `stock`, `account`, `delivery` і `mail`.
* **WooCommerce** 3.5 або новіший. Модуль тестується на поточній лінійці 11.x
  (11.2.2 під час розробки).
* **HTTPS на боці магазину.** WooCommerce 11 приймає облікові дані REST лише
  через SSL: той самий запит звичайним HTTP отримує відповідь `401`. URL
  магазину має бути доступним через TLS; `http://` приймається лише для локальних
  імен `localhost`, `127.0.0.1`, `::1`, `odoo` і `wordpress`.
* **Публічна HTTPS-адреса Odoo**, якщо потрібні вебхуки. Це значення системного
  параметра `web.base.url`; з нього будується адреса вебхука.
* **Python**: лише бібліотека `requests`, яка входить до кожної інсталяції Odoo.
  Нічого не потрібно ставити через pip, жодних модулів OCA.
* Процес планувальника Odoo (cron) має працювати (типовий `odoo-bin` працює),
  інакше черга ніколи не виконується.

## 3. Встановлення

1. Скопіюйте каталог модуля в один із каталогів доповнень (addons) сервера Odoo:

   ```bash
   cp -R rex_woocommerce_connector /opt/odoo/addons/
   ```

   Каталог модуля має містити обидва файли — `__init__.py` і `__manifest__.py`;
   Odoo ігнорує шлях доповнень, у якому немає такого модуля.

2. Перезапустіть Odoo і оновіть список застосунків:

   **Застосунки > Оновити список застосунків**, знайдіть *Two-way Sync for WooCommerce*
   і натисніть **Встановити**.

3. Під час встановлення створюються:

   * групи доступу **WooCommerce / Користувач** і **WooCommerce / Менеджер**;
   * сім планових дій зі [розділу 8](#8-планові-дії-та-ручна-синхронізація);
   * типові параметри конфігурації з [розділу 20](#20-параметри-конфігурації).

4. У головному меню з'являється застосунок **WooCommerce** з пунктами
   **Магазини**, **Завдання**, **Журнал активності** і **Доставки вебхуків**.

Більше на сервері нічого не потрібно: жодного кроку збірки, жодного додаткового
сервісу, жодної таблиці, яку треба створювати вручну.

### Перевірка встановлення

```text
1. WooCommerce > Магазини > Створити   форма відкривається без помилки
2. Перевірити з'єднання               стан стає "Підключено"
3. Синхронізувати зараз               сповіщення показує кількість завдань
4. WooCommerce > Завдання             завдання з'являються як "У черзі", далі "Готово"
5. WooCommerce > Журнал активності    з'являються рядки "Imported N products."
```

## 4. Підготовка WooCommerce

### 4.1 Постійні посилання і HTTPS

REST API живе за адресою `/wp-json/`, що працює лише з "гарними" постійними
посиланнями: у **Налаштування > Постійні посилання** має бути будь-що, крім
*Простий*. Магазин також має працювати через HTTPS, як сказано в
[розділі 2](#2-вимоги).

### 4.2 Ключ REST API

1. У WordPress відкрийте **WooCommerce > Налаштування > Додатково > REST API**.
2. Натисніть **Додати ключ**:
   * Опис: `Odoo` (будь-який);
   * Користувач: адміністратор або менеджер магазину з правами читання й запису;
   * Права: **Читання/Запис**.
3. Натисніть **Згенерувати ключ API** і негайно скопіюйте обидва значення:
   ключ споживача (`ck_...`) і секрет споживача (`cs_...`). Секрет показується
   лише один раз.

Права читання/запису потрібні, бо конектор надсилає залишки й нотатки
відстеження та створює товари під час експорту.

### 4.3 Пароль застосунку WordPress (лише для експорту зображень)

Зображення товарів завантажуються до медіатеки WordPress, а ядро WordPress не
приймає ключ споживача WooCommerce для цієї точки. Якщо потрібно експортувати
зображення з Odoo, створіть користувача WordPress із правом *upload_files* і
пароль застосунку для нього (**Користувачі > Профіль > Паролі застосунків**), потім
заповніть поля **Користувач WordPress** і **Пароль застосунку WordPress** у
магазині. Без них каталог усе одно експортується; пропускається лише крок із
зображенням, із попередженням у журналі активності.

Імпорт зображень (WooCommerce → Odoo) не потребує додаткових даних: він
завантажує публічну адресу зображення.

### 4.4 Планувальник WordPress

WooCommerce доставляє вебхуки через псевдо-cron WordPress, який запускається під
час відвідувань сайту. У магазині з малим трафіком доставка може запізнюватися.
Конектор це враховує: опитування замовлень виправляє все, що пропустив вебхук,
тому робочий cron WordPress — це покращення затримки, а не вимога.

## 5. Створення магазину в Odoo

**WooCommerce > Магазини > Створити**. Усі поля нижче є на формі магазину.

| Поле | Значення |
| --- | --- |
| **Назва** | Мітка, яка використовується лише в Odoo. |
| **URL магазину** | Коренева адреса WordPress, наприклад `https://shop.example.com`. Завершальний слеш і `/wp-json` у кінці видаляються; якщо схеми немає, додається `https://`. Звичайний `http` приймається лише для локальних імен. |
| **Ключ споживача** / **Секрет споживача** | Ключ REST API з WooCommerce. Видимий лише групі *Менеджер*. |
| **Користувач WordPress** / **Пароль застосунку WordPress** | Необов'язково; потрібно лише для експорту зображень товарів. Лише *Менеджер*. |
| **Перевіряти TLS-сертифікат** | Залиште позначеним. Знімайте позначку лише для локального магазину із самопідписаним сертифікатом: тоді облікові дані передаються незахищеним з'єднанням. |
| **Версія WooCommerce**, **Валюта**, **Ціни введено з податком** | Лише читання, заповнюється кнопкою **Перевірити з'єднання**. |
| **Склад** | Джерело залишку, що надсилається, і призначення залишку, що вивантажується. Типово — перший склад компанії; якщо поле порожнє, конектор використовує той самий склад. |
| **Прайс-лист** | Застосовується до імпортованих замовлень. |
| **Типова категорія товарів** | Категорія товарів, створених із WooCommerce. Якщо порожня — перша категорія товарів у базі. |
| **Товар для доставки** | Товар для рядків доставки в імпортованих замовленнях. Якщо порожній, конектор знаходить або створює послугу з внутрішнім кодом `WOO-SHIPPING`. |
| **Товар для доплат** | Товар для рядків доплат (fee) в імпортованих замовленнях. Якщо порожній — послуга з кодом `WOO-FEE`. |
| **Джерело запасів** | `Odoo`, `WooCommerce` або `Вимкнено`. Див. [розділ 11](#11-синхронізація-запасів). |
| **Тип кількості** | `Доступно (на складі мінус зарезервовано)` (типово) або `На складі`. *Доступно* — безпечний вибір: запас, зарезервований під підтверджені замовлення, уже продано, і повторна публікація призвела б до перепродажу. |
| **Імпортувати товари з WooCommerce** | Керує опитувачем товарів і товарною частиною **Синхронізувати зараз**. Вебхуки `product.*` обробляються для кожного активного магазину. |
| **Експортувати товари в WooCommerce** | Керує плановою дією експорту. Також не дає пізнішому імпорту перезаписати ціну продажу Odoo ціною WooCommerce (перший імпорт завжди приносить ціну). |
| **Синхронізувати замовлення** | Керує опитувачем замовлень і **Синхронізувати зараз**; вебхуки `order.*` обробляються для кожного активного магазину. |
| **Синхронізувати клієнтів** | Керує плановою дією імпорту клієнтів; вебхуки `customer.*` обробляються для кожного активного магазину. |
| **Синхронізувати повернення** | Імпортує повернення WooCommerce як кредит-ноти, щойно на замовлення продажу виставлено рахунок. Див. [розділ 14](#14-повернення-коштів). |
| **Надсилати номери відстеження в WooCommerce** | Вмикає надсилання даних виконання. |
| **Підтверджувати імпортовані замовлення** | Позначено: імпортовані замовлення підтверджуються. Знято: залишаються комерційними пропозиціями. |
| **Створювати відсутні товари** | Позначено: товар із замовлення, який не вдалося зіставити, створюється як мінімальний товар. Знято: імпорт замовлення завершується зрозумілою помилкою. |
| **Допуск загальної суми** | Допустима різниця між сумою Odoo і сумою WooCommerce, типово `0.02`. Більша різниця записується як попередження. |
| **Максимум спроб завдання** | Кількість спроб до остаточної відмови завдання, типово `5`. |
| **URL вебхука** | Обчислюється з `web.base.url`; можна скопіювати. |
| **Секрет вебхука** | Випадковий секрет, створений разом із магазином; використовується для перевірки заголовка `X-WC-Webhook-Signature`. Лише *Менеджер*. |
| **Зареєстровані вебхуки** | JSON-зведення останнього запуску **Зареєструвати вебхуки**. |
| **Остання синхронізація товарів**, **замовлень**, **Останній експорт товарів** | Водяні знаки (UTC), що записуються після успішного запуску. Опитування, у якому запис не вдався з причини, що може зникнути (мережа, блокування), зберігає старий водяний знак, тому наступне опитування повторює спробу; відмова, яка не зміниться (інша валюта, незіставлений товар при вимкненому створенні товарів), журналюється й не затримує водяний знак. |
| **Завдання в черзі**, **Завдання з помилкою**, **Остання помилка** | Показані у списку та на формі. |

**URL магазину фіксується**, щойно синхронізовано перший запис: він є частиною
ідентичності кожного рядка відповідності, тому зміна викликає помилку. Якщо
магазин справді переїхав, створіть новий запис магазину.

## 6. Перевірка з'єднання

Натисніть **Перевірити з'єднання**. Кнопка:

1. викликає `GET /wp-json/wc/v3/system_status` із збереженими обліковими даними;
2. читає версію WordPress, версію WooCommerce і валюту магазину;
3. активує валюту в Odoo, якщо вона існує, але архівована;
4. читає `GET /wp-json/wc/v3/settings/tax/woocommerce_prices_include_tax` і
   зберігає ознаку *Ціни введено з податком*;
5. записує стан **Підключено**, версію WooCommerce, дату й очищає **Останню помилку**.

У разі помилки магазин позначається як **Помилка**, повідомлення зберігається в
**Останній помилці** і виникає `UserError`, щоб причина була видна одразу. Дві
типові причини — неправильний ключ і магазин без HTTPS (див.
[розділ 23](#23-усунення-несправностей)).

`prices_include_tax` використовується тоді, коли експорт каталогу записує ціну
назад у WooCommerce (надсилається ціна з податком). Рядки замовлень перераховувати
не потрібно: WooCommerce передає їх без податку в кожному магазині (див.
[розділ 12](#12-замовлення)).

## 7. Вебхуки

Натисніть **Зареєструвати вебхуки** після успішної перевірки з'єднання.

* Передумова: `web.base.url` має бути **публічною HTTPS-адресою** Odoo. Кнопка
  відмовляється працювати, якщо обчислена адреса вебхука не `https://`, бо
  WordPress передавав би дані замовлень відкритим текстом або не передавав би
  взагалі.
* Точка входу: `https://<ваш odoo>/woocommerce/webhook/<id магазину>`.
* Реєструються теми: `order.created`, `order.updated`, `order.deleted`,
  `product.created`, `product.updated`, `product.deleted`, `customer.created`,
  `customer.updated`. У WooCommerce немає теми для повернень: повернення змінює
  своє замовлення й надходить як `order.updated`.
* Кожен вебхук має назву `Odoo <тема>` і несе **секрет вебхука** магазину.
  Кнопка зберігає JSON-зведення в **Зареєстрованих вебхуках**.
* Повторне натискання кнопки створює лише ті теми, яких для цієї адреси ще
  бракує; наявні вебхуки зберігаються.

Як обробляється доставка:

1. Точка входу перевіряє підпис HMAC-SHA256 **сирого тіла** за заголовком
   `X-WC-Webhook-Signature` (порівняння сталого часу) і відповідає `401`, якщо
   підпис не збігається.
2. Доставки дедуплікуються за `X-WC-Webhook-Delivery-ID`; повторна відповідає
   `200` і нічого не робить. (`X-WC-Webhook-ID` — це id самого вебхука, він
   однаковий для кожної доставки, тому не може ідентифікувати окрему подію.)
3. Непідписана перевірка `webhook_id=<id>`, яку WooCommerce надсилає під час
   створення або збереження вебхука, і порожнє тіло отримують відповідь `200` і
   далі не обробляються.
4. Дані зберігаються в **Доставках вебхуків**, завдання типу *Обробити вебхук*
   ставиться в чергу з найвищим пріоритетом, і точка входу негайно відповідає
   `200`. Сам імпорт виконується в черзі.

Оскільки доставка підтверджується до імпорту, повільний Odoo ніколи не змушує
WordPress повторювати спробу. Якщо щось не вдалося, завдання видно в **Завданнях**
і в **Журналі активності**.

## 8. Планові дії та ручна синхронізація

Модуль встановлює сім планових дій (**Налаштування > Технічні > Автоматизація >
Планові дії**, фільтр *WooCommerce*):

| Назва | Інтервал | Активна після встановлення | Що робить |
| --- | --- | --- | --- |
| WooCommerce: process the synchronisation queue | 1 хвилина | так | Бере й виконує до 20 завдань у черзі (`rex_woocommerce_connector.queue_batch`). |
| WooCommerce: poll orders | 10 хвилин | так | Ставить опитування `order_import` для кожного активного магазину з *Синхронізувати замовлення*. |
| WooCommerce: poll products | 60 хвилин | так | Ставить опитування `product_import` для кожного активного магазину, який імпортує товари. |
| WooCommerce: push stock | 30 хвилин | **ні** | Ставить `stock_push` для магазинів, де джерело запасів — Odoo. |
| WooCommerce: export products | 30 хвилин | **ні** | Ставить `product_export` для магазинів, які експортують товари. |
| WooCommerce: pull stock | 15 хвилин | **ні** | Ставить `stock_pull` для магазинів, де джерело запасів — WooCommerce. |
| WooCommerce: import customers | 120 хвилин | **ні** | Ставить `customer_import` для магазинів із *Синхронізувати клієнтів*. |

Чотири дії — **push stock**, **export products**, **pull stock** та **import
customers** — встановлюються **вимкненими**: кожна з них пише в живу систему або
читає цілу таблицю, тому вмикаються лише свідомим рішенням.

Кнопки на формі магазину ставлять роботу в чергу негайно й одразу повертають
керування; сповіщення каже, що саме поставлено в чергу, а далі працює черга:

* **Синхронізувати зараз** — опитування замовлень, якщо позначено *Синхронізувати
  замовлення*; опитування товарів, якщо позначено *Імпортувати товари*; і повне
  надсилання залишків, якщо джерело запасів — **Odoo**;
* **Експортувати товари** — завдання `product_export`;
* **Імпортувати клієнтів** — завдання `customer_import`.

## 9. Імпорт каталогу

Опитувач товарів читає `GET /wp-json/wc/v3/products` у порядку id, імпортує кожен
товар і потім варіанти кожного варіативного товару. Опитувач надсилає
`modified_after` із водяним знаком *Остання синхронізація товарів* і
`dates_are_gmt=true` (без нього WooCommerce порівнює дату з місцевим часом сайту),
тому після першого запуску читаються лише товари, змінені з моменту попереднього успішного
опитування. Перший запуск читає весь каталог — це те, що потрібно на порожній базі,
і те, що на великому каталозі варто планувати поза робочими годинами.

Для кожного товару конектор створює або оновлює один `product.template`:

| Поле Odoo | Джерело |
| --- | --- |
| Назва | Назва WooCommerce (HTML-сутності розкодовано) |
| Внутрішній код | SKU; також використовується один раз, щоб прийняти наявний товар Odoo з таким самим кодом |
| Штрихкод | Штрихкод WooCommerce |
| Ціна продажу | Ціна WooCommerce під час першого імпорту; надалі **лише коли "Експортувати товари в WooCommerce" знято**, інакше перемагає ціна Odoo і не перезаписується |
| Тип | `Товар` (споживний або запасний), з ознакою *Відстежувати запаси*, коли WooCommerce керує залишками |
| Категорія | *Типова категорія товарів* магазину, інакше перша категорія товарів |
| Опис для продажу | Короткий і повний опис, теги прибрано, до 4000 символів |
| Вага | Вага WooCommerce |
| Зображення | **Перше** зображення товару, завантажене з публічної адреси (зображення понад 10 МБ пропускаються) |
| Атрибути | Кожен атрибут зі своїми значеннями стає `product.attribute` (створює варіанти) зі значеннями |
| Варіанти | Зіставляються за комбінацією атрибутів у шаблоні; оновлюється їхній SKU. Їхня ціна зберігається як додаткова ціна значення атрибута (під час першого імпорту і під час кожного імпорту, коли експорт вимкнено). Odoo може задати окремі ціни варіантів лише для товарів з **одним** змінним атрибутом; якщо таких атрибутів кілька, ціни варіантів не змінюються, а в журнал записується попередження |

Правила зіставлення, за порядком:

1. рядок відповідності для цього магазину й цього id WooCommerce — звичайний випадок;
2. SKU — лише щоб прийняти товар, ще не зіставлений із цим магазином;
3. інакше створюється новий товар.

Товар, який не вдалося зіставити або записати, журналюється, і імпорт переходить до
наступного: один зламаний товар ніколи не зупиняє опитування. Незіставлені
варіанти записуються як попередження; конектор не створює варіантів в Odoo.

Видалення товару в WooCommerce **архівує** зіставлений товар Odoo
(`active = false`) через вебхук `product.deleted`; в Odoo нічого ніколи не
видаляється. Архівований товар зникає зі звичайного пошуку, але зберігає історію
продажів, і рядок рівня info у журналі активності фіксує архівування.

## 10. Експорт каталогу

Сервіс експорту надсилає в WooCommerce **товари** (не послуги) компанії магазину,
які **продаються в Odoo**: назву, внутрішній код як SKU, ціну продажу як
`regular_price`, опис для продажу, штрихкод і статус `publish`, після чого
завантажує основне зображення через медіатеку WordPress, якщо в магазині
налаштовано користувача WordPress і пароль застосунку. Зображення, яке не
змінилося після останнього завантаження, повторно не завантажується.

Що саме записується, визначає власник товару:

* товари, **створені в Odoo** (або прийняті за SKU під час першого експорту),
  належать Odoo й оновлюються під час кожного експорту;
* товари, **імпортовані з WooCommerce**, належать магазину, і експорт ніколи їх не
  переписує, тому їхній HTML-опис, галерея та звичайна й акційна ціни залишаються
  такими, як їх задав продавець;
* згенеровані товари `WOO-SHIPPING` і `WOO-FEE`, а також будь-які послуги ніколи
  не експортуються.

Експорт запускається кнопкою **Експортувати товари** на формі магазину (усі
придатні товари) або плановою дією *WooCommerce: export products*, яка
встановлюється **вимкненою** (30 хвилин) і експортує товари, змінені після її
попереднього запуску.

Перед створенням товару експорт шукає у WooCommerce товар із таким самим SKU і
**приймає** його замість створення дубліката, тому перший експорт наявного
каталогу прив'язує товари Odoo до товарів WooCommerce, які вже несуть їхній
внутрішній код.

Що важливо для обліку:

* експорт завжди записує **простий** товар; варіанти не експортуються;
* надсилається **ціна продажу** Odoo, а не ціна з прайс-листа;
* експорт ніколи не видаляє товар у WooCommerce;
* крок із зображенням пропускається з попередженням у журналі активності, якщо
  облікові дані WordPress відсутні або завантаження не вдалося.

## 11. Синхронізація запасів

Напрямок визначає **Джерело запасів**:

| Значення | Надсилання (Odoo → WooCommerce) | Вивантаження (WooCommerce → Odoo) |
| --- | --- | --- |
| `Odoo` | Увімкнено; запускається плановою дією та кнопкою **Синхронізувати зараз** | Вимкнено |
| `WooCommerce` | Вимкнено | Увімкнено, коли поставлено завдання вивантаження |
| `Вимкнено` | Вимкнено | Вимкнено |

**Надсилання.** Для кожного зіставленого товару магазину конектор обчислює
кількість на складі магазину (локація `WH/Stock` і її дочірні) — або фактичний
залишок, або доступну кількість, залежно від **Типу кількості** — і надсилає
`manage_stock: true` разом із `stock_quantity`:

* простий товар: `PUT /wp-json/wc/v3/products/<id>`;
* варіант: `PUT /wp-json/wc/v3/products/<id батька>/variations/<id>`.

Надсилаються лише **запасні** товари: споживний товар або послуга не мають
залишків в Odoo, тому публікувати нічого. Батьківський варіативний товар
пропускається в обох напрямках: залишок несуть його варіанти. Від'ємна доступна
кількість надсилається як `0`. Товар, який не вдався, журналюється, і
надсилання продовжується. На кожен товар береться порадницьке блокування
PostgreSQL, тому два паралельні завдання не можуть перезаписати одне одного
застарілим значенням.

Планова дія надсилання залишків **вимкнена** після встановлення модуля, щоб свіжа
інсталяція ніколи не записала кількості в живий магазин до того, як хтось
перевірив склад і відповідності. Увімкніть її, коли будете готові.

**Вивантаження.** Коли джерело запасів — WooCommerce, вивантаження читає
`stock_quantity` кожного зіставленого товару — з точки варіантів, якщо
відповідність вказує на варіант — і створює підтверджене **коригування запасів** у
локації складу магазину, тому рух простежуваний і оцінений, коли ввімкнено
автоматичну оцінку. Воно запускається плановою дією *WooCommerce: pull stock*,
встановленою **вимкненою** (15 хвилин), або вручну поставленим завданням
`stock_pull`.

## 12. Замовлення

Замовлення надходять двома шляхами:

* **вебхуки** — `order.created`, `order.updated`, `order.deleted`, обробляються
  чергою протягом хвилини;
* **опитування** — кожні 10 хвилин `GET /wp-json/wc/v3/orders` з
  `modified_after=<остання синхронізація замовлень>`, `dates_are_gmt=true` і
  `orderby=id&order=asc` для
  кожного активного магазину з *Синхронізувати замовлення*.

Обидва шляхи ведуть до того самого ідемпотентного імпорту, тому вебхук і опитувач
можуть "перегони" влаштувати без дублювання: у таблиці відповідностей є унікальне
обмеження на (магазин, id WooCommerce).

Імпортоване замовлення стає `sale.order`:

| Поле Odoo | Джерело |
| --- | --- |
| Клієнт | див. [розділ 13](#13-клієнти) |
| Дата замовлення | `date_created_gmt` (naive UTC), інакше поточний час |
| Посилання клієнта | Номер замовлення WooCommerce |
| Документ-джерело | `WooCommerce #<номер>` |
| Прайс-лист | *Прайс-лист* магазину, якщо заданий |
| Внутрішня нотатка | Нотатка клієнта, назва способу оплати й посилання на замовлення WooCommerce |
| Рядки | див. нижче |
| Статус | підтверджене, якщо позначено *Підтверджувати імпортовані замовлення*, інакше комерційна пропозиція |

Обробка рядків:

* **рядок товару**: кількість із `quantity`, ціна за одиницю `subtotal / quantity`
  і відсоток знижки, обчислений із `(subtotal - total) / subtotal` — саме так
  зберігається купон, який зменшує рядок;
* **рядок доставки**: **Товар для доставки** магазину, кількість 1, ціна з
  `shipping_lines[].total`;
* **рядок доплати**: **Товар для доплат** магазину, інакше послуга з внутрішнім
  кодом `WOO-FEE`, кількість 1, ціна з `fee_lines[].total`;
* **податки**: кожен податок рядка WooCommerce зіставляється через карту податків
  магазину. Податки зіставляються **за ставкою** з податками продажу компанії
  магазину, з перевагою податку з рахунком, а далі — типового податку продажу
  компанії. Рядок, податок якого не має відповідника в Odoo, імпортується без
  цього податку.

WooCommerce передає проміжні й підсумкові суми рядків замовлення **без податку** в
кожному магазині, зокрема в магазинах, де ціни введено з податком, тому суми рядків
використовуються як ціни без податку, а Odoo додає зіставлені податки.
Зіставляються лише ті податки Odoo, які *не* включено в ціну. *Ціни введено з
податком* має значення тоді, коли експорт каталогу записує ціну назад у
WooCommerce. У магазині з цінами, введеними з податком, замовлення може
відрізнятися від WooCommerce на одну копійку, бо WooCommerce округлює ціну з
податком.

Після створення замовлення конектор порівнює суму Odoo із сумою WooCommerce
(`total`). Різниця, більша за **Допуск загальної суми**, записується в журнал
активності як попередження (`Order SO…: Odoo total … differs from WooCommerce
total …`), а не приймається мовчки. Звичайні причини — відсутня в Odoo ставка
податку, складна (compound) ставка, округлення на одну копійку в магазині з цінами,
введеними з податком, або купон, який зменшив доставку чи доплати.

Зміна статусу вже імпортованого замовлення **не** переписує замовлення продажу:
оновлюються власні поля конектора (статус WooCommerce, ознака оплати, сума).
Виняток — `cancelled` і вебхук `order.deleted`, які скасовують замовлення
продажу, якщо воно ще не виконане й не скасоване. Є й зворотний напрямок:
скасування замовлення продажу в Odoo ставить завдання статусу, яке переводить
замовлення WooCommerce у `cancelled`, якщо існує відповідність.

Коли позначено *Створювати відсутні товари*, а рядок замовлення не має ні
відповідності, ні збігу за SKU, конектор створює мінімальний товар **і одразу
ставить його у відповідність**, тому пізніший експорт каталогу не створить другу
копію того самого товару в WooCommerce.

Валюта: замовлення у валюті, відмінній від валюти магазину, відхиляється з
помилкою в журналі активності; мультивалютні замовлення у версії 1.0 не
підтримуються.

Купони: рядки `coupon_lines` як такі не імпортуються. Знижка у відсотках або
фіксована знижка, яка зменшує підсумок рядка, відображається у знижці рядка; купон,
який зменшує доставку або доплати, робить суму Odoo відмінною, і це фіксується
перевіркою суми.

## 13. Клієнти

Клієнт зіставляється в такому порядку:

1. рядок відповідності для цього магазину й цього id клієнта WooCommerce;
2. наявний партнер Odoo з такою ж адресою електронної пошти (без урахування
   регістру);
3. новий `res.partner`.

Під час створення партнер отримує ім'я, e-mail, телефон і платіжну адресу (вулиця,
вулиця 2, місто, індекс, країна, область) та ознаку клієнта. У наявного партнера
платіжна адреса заповнює лише **порожні** поля — Odoo ніколи не перезаписує
адресу, яку хтось ввів.

Гостьове замовлення (`customer_id` 0) підтримується: партнер знаходиться за
платіжним e-mail або створюється, але **рядок відповідності не створюється**, тому
пізніший справжній клієнт із тим самим e-mail не буде мовчки приєднаний до
гостьового запису.

Клієнти також створюються неявно під час імпорту замовлень, і це звичайний шлях:
конектор читає `GET /wp-json/wc/v3/customers/<id>` і, якщо клієнта прочитати не
вдалося, використовує блок платіжних даних замовлення. Вебхуки `customer.created` і
`customer.updated` імпортують клієнта без замовлення. Масовий імпорт доступний
кнопкою **Імпортувати клієнтів** і плановою дією *WooCommerce: import customers*
(встановлюється вимкненою, кожні 120 хвилин); обидва ставлять завдання
`customer_import`, яке читає весь список клієнтів.

Адреса доставки замовлення у версії 1.0 не створюється як дочірній контакт;
синхронізується платіжна адреса клієнта. Це зазначено в
[розділі 22](#22-відомі-обмеження-версії-10).

## 14. Повернення коштів

У WooCommerce немає вебхука для повернень: повернення змінює своє замовлення.
Щоразу, коли замовлення читається — 10-хвилинним опитуванням або вебхуком
`order.updated` — і містить повернення без кредит-ноти, у чергу ставиться завдання
*Імпортувати повернення*. Це завдання читає кожне повернення замовлення й створює
одну **кредит-ноту клієнту** (`out_refund`) на кожне повернення WooCommerce. Для
замовлення, на яке ще не виставлено рахунок, нічого не ставиться в чергу; його
повернення буде підхоплено під час наступної зміни замовлення після виставлення
рахунку.

Передумови:

* замовлення імпортоване (інакше повернення журналюється й пропускається);
* замовлення продажу має **проведений рахунок** (замовлення без рахунку
  журналюється як попередження й пропускається).

Як будується кредит-нота:

* **повернення з рядками**: кожен рядок кредитується своєю кількістю за
  `total / quantity` (без податку), з податками відповідного рядка рахунку (або
  податками продажу товару, якщо рядок рахунку не знайдено); варіант
  зіставляється за своїм id варіанта. Коли сума повернення включає доставку або
  доплати, різниця додається одним рядком без податку, тому сума кредит-ноти
  завжди дорівнює сумі повернення;
* **повернення лише суми** (ручне повернення в адмінці WooCommerce, без рядків):
  один рядок із сумою повернення і **без податку**. Конектор кредитує рівно те, що
  клієнт отримав назад; податкова частина такого повернення **не** сторнується.
  Журнал активності фіксує створену кредит-ноту, тому бухгалтер може її
  скоригувати. Це свідома поведінка версії 1.0, задокументована, щоб її не виявили
  під час аудиту;
* кредит-нота проводиться негайно, з журналом і валютою рахунку;
* посилання — `WooCommerce refund <id повернення>`, і воно перевіряється перед
  створенням, тому те саме повернення ніколи не створить другу кредит-ноту;
  повернення, яке не вдалося провести, не залишає після себе чернетки.

Імпорт повернень нічого не повертає на склад, а оплата й бухгалтерське зіставлення
повернення не автоматизуються.

## 15. Номери відстеження

Коли в Odoo підтверджується **вихідна** доставка, конектор ставить завдання
`fulfilment_push`. Завдання читає номер відстеження доставки
(`carrier_tracking_ref`) і додає **нотатку клієнту** до замовлення WooCommerce:

```text
Shipment WH/OUT/00012 with DHL. Tracking number: 1234567890
```

Назва перевізника додається, якщо в доставки є перевізник, а частина з номером
відстеження пропускається, якщо номер порожній. Нотатка видна клієнту на сторінці
замовлення WooCommerce і в листах "нотатка до замовлення".

Вимоги: позначено *Надсилати номери відстеження в WooCommerce*, вихідна доставка
пов'язана із замовленням продажу, і існує відповідність між цим замовленням і
магазином. Помилка ніколи не блокує доставку: вона перехоплюється, журналюється й
залишається в черзі, а доставка залишається підтвердженою.

Якщо в одній базі кілька магазинів, обробник доставки ставить завдання для першого
активного магазину з увімкненим *Надсилати номери відстеження*; далі завдання
знаходить відповідність замовлення для цього магазину. Якщо те саме замовлення
існує в кількох магазинах, нотатка піде до магазину, який обрав обробник. Це
обмеження версії 1.0.

## 16. Черга завдань

Кожен крок синхронізації — це рядок `woo.job`. Екран черги (**WooCommerce >
Завдання**) показує назву, магазин, тип, стан, кількість спроб, наступний запуск,
час завершення й тривалість, дозволяє пошук і групування за станом, типом і
магазином.

Стани:

| Стан | Значення |
| --- | --- |
| У черзі | Чекає своєї черги; після помилки `Наступний запуск` у майбутньому |
| Виконується | Взяте працівником; після завершення оренди повертається в чергу |
| Готово | Завершене успішно |
| Помилка | Відхилене остаточно після *Максимуму спроб завдання* |
| Скасовано | Скасоване вручну |

Виконання:

* планова дія черги працює **щохвилини** й бере до
  `rex_woocommerce_connector.queue_batch` завдань (типово 20) через
  `FOR UPDATE SKIP LOCKED`, тому кілька працівників Odoo ніколи не виконують те
  саме завдання;
* завдання, яке перебуває в стані **Виконується** довше за
  `rex_woocommerce_connector.job_lease_minutes` (типово 30), вважається загиблим і
  повертається в **У черзі**, тому працівник, що впав, не блокує чергу;
* завдання, що падає, повторюється з експоненційною затримкою від 5 секунд до
  5 хвилин, доки не досягне *Максимуму спроб завдання* (поле магазину, типово 5),
  після чого відхиляється остаточно;
* кожна спроба зберігається з помилкою в **Останній помилці**, а виняток
  записується в журнал активності з HTTP-статусом і кодом помилки WooCommerce.

Ручні дії на формі завдання: **Повторити** (помилка або скасовано → у черзі,
лічильник спроб скидається), **Скасувати** (у черзі або помилка → скасовано),
**Виконати зараз** (виконує завдання з черги негайно в поточній транзакції).

Вкладка **Payload** показує JSON, з яким створено завдання, а **Остання помилка** —
виняток останньої спроби.

## 17. Журнал активності

**WooCommerce > Журнал активності** — операційна історія конектора. В інтерфейсі
він доступний лише для читання.

| Рівень | Коли пишеться |
| --- | --- |
| Info | Пакет завершено: "Imported N products.", "Pushed stock for N products.", створено кредит-ноту, надіслано нотатку відстеження |
| Warning | Не вдалося обробити товар, зображення або варіант; сума замовлення відрізняється; повернення пропущено |
| Error | Завдання впало: повідомлення винятку, HTTP-статус, код помилки WooCommerce і фрагмент payload |

Кожен рядок зберігає дату, магазин, рівень, повідомлення, HTTP-статус, код
помилки WooCommerce, URL, завдання, запис Odoo і payload (до 20 000 символів).
Доступні фільтри **Помилки** й **Попередження** та групування за рівнем і
магазином.

Завдання, що впало, завжди створює рівно один рядок помилки, тому "що зламалося і
чому" стає зрозуміло без читання серверного логу.

## 18. Доставки вебхуків

**WooCommerce > Доставки вебхуків** зберігає кожну прийняту доставку: дату,
магазин, тему, id ресурсу WooCommerce, ключ дедуплікації (`X-WC-Webhook-Delivery-ID`), стан
(*У черзі* → *Готово*), дату обробки і сирий payload. Доставка, завдання якої впало,
залишається в **У черзі** — причина в **Останній помилці** створеного нею завдання.

Використовуйте цей екран, щоб відповісти на два питання: *чи доставив WordPress?*
і *чи оброблено доставку?* Доставка в стані **У черзі**, завдання якої ще
очікує, — це нормально на кілька секунд; доставка, що застрягла в **У черзі**,
означає, що планова дія черги не працює.

## 19. Права доступу

| Група | Права |
| --- | --- |
| WooCommerce / Користувач | Читає магазини, завдання, журнал активності, доставки вебхуків і таблиці відповідностей. Кнопки на формі магазину записують у запис магазину, тому скористатися ними може лише учасник групи *Менеджер*. |
| WooCommerce / Менеджер | Повне створення, редагування й видалення об'єктів конектора; бачить ключ споживача, секрет споживача, секрет вебхука й облікові дані WordPress. |

Лише група *Менеджер* бачить облікові дані, за допомогою яких можна читати або
змінювати магазин, — саме тому груп дві.

## 20. Параметри конфігурації

Інсталятор записує ці типові значення в **Налаштування > Технічні > Параметри >
Системні параметри**. У версії 1.0 код читає перші два; інші записуються
інсталятором і зарезервовані для наступних версій:

| Параметр | Типово | Читається у 1.0 | Значення |
| --- | --- | --- | --- |
| `rex_woocommerce_connector.queue_batch` | 20 | так | Скільки завдань виконує один запуск черги. |
| `rex_woocommerce_connector.job_lease_minutes` | 30 | так | Скільки завдання може перебувати в стані *Виконується* до повернення в чергу. |
| `rex_woocommerce_connector.job_max_attempts` | 5 | ні | Зарезервовано. |
| `rex_woocommerce_connector.batch_size` | 100 | ні | Зарезервовано; сам клієнт API обмежує пакет 100 об'єктами. |
| `rex_woocommerce_connector.total_tolerance` | 0.02 | ні | Зарезервовано; використовуйте поле **Допуск загальної суми** магазину. |

Поведінка окремого магазину налаштовується на формі магазину, а не тут:
**Допуск загальної суми** й **Максимум спроб завдання** — поля магазину.

## 21. Сторінка стану

Авторизований користувач може відкрити

```text
https://<ваш odoo>/woocommerce/status
```

Сторінка повертає звичайний текст із блоком на кожен магазин: стан з'єднання, URL,
кількість завдань у черзі й кількість завдань із помилкою. Вона призначена для
швидкої перевірки під час підтримки й для моніторингу; вона ніколи не показує
облікових даних і нічого не записує.

## 22. Відомі обмеження версії 1.0

Це свідомі обмеження першої версії, а не помилки, про які треба повідомляти:

* **Лише Odoo 19.0 і 20.0.** Шар сумісності покриває ці дві версії; старіші не
  підтримуються.
* **Немає рушія зіставлення метаполів.** Додаткові метадані WooCommerce не
  імпортуються.
* **Рядки купонів не імпортуються.** Знижка рядка зберігає вартість купона,
  застосованого до товарів; купон на доставку або доплати робить суму відмінною, і
  це фіксує перевірка суми.
* **Немає мультивалютних замовлень.** Замовлення у валюті, відмінній від валюти
  магазину, пропускається з помилкою.
* **Немає комплектів і BoM.** Обробляються лише прості товари та варіанти.
* **Немає підписок, бронювань і POS-плагінів.** Їхні замовлення та додаткові
  об'єкти імпорт не розуміє.
* **Один склад на магазин.** Залишки читаються з локації складу поля *Склад* і
  записуються туди ж.
* **Складні (compound) податки не зіставляються.** Рядки замовлень імпортуються
  із сумами без податку та зіставленими відсотковими податками; складний податок
  WooCommerce може зробити суму Odoo відмінною, і це фіксує перевірка суми.
  Основна тестована конфігурація — ціни без податку.
* **Додаткові планові дії встановлюються вимкненими.** Експорт товарів,
  вивантаження запасів, надсилання запасів та імпорт клієнтів треба вмикати вручну,
  бо вони пишуть у живу систему або читають весь список клієнтів.
* **Повернення чекають на рахунок.** Повернення замовлення без рахунку
  імпортується під час наступної зміни замовлення після виставлення рахунку.
* **Варіанти лише зіставляються, не створюються.** Варіант без відповідного
  варіанта Odoo записується як попередження.
* **Немає повернення на склад і зіставлення платежів.** Повернення створює
  кредит-ноту; запаси й платежі залишаються процесами Odoo.
* **Адреса доставки не є дочірнім контактом.** Синхронізується лише платіжна
  адреса.
* **Як статус замовлення надсилається лише скасування.** Надсилання номера
  відстеження додає нотатку до замовлення; Odoo не надсилає статуси "в обробці" або
  "завершено".

## 23. Усунення несправностей

| Симптом | Причина й рішення |
| --- | --- |
| `401 Unauthorized`, код `woocommerce_rest_cannot_view` | Неправильний ключ або секрет споживача, або магазин відкривається через **звичайний HTTP**. WooCommerce 11 автентифікує лише через SSL: використовуйте `https://`. У локальному стеку перевірте, що сертифікат довірений, або зніміть *Перевіряти TLS-сертифікат* для самопідписаного. |
| `404` з кодом `rest_no_route` | Неправильний URL магазину. Це має бути корінь інсталяції WordPress (`https://shop.example.com`), а не сторінка, не `/shop` і не сам шлях `/wp-json/wc/v3`. |
| `Перевірити з'єднання` працює, `Зареєструвати вебхуки` відмовляється | `web.base.url` не є публічною HTTPS-адресою. Задайте її в **Налаштування > Технічні > Параметри > Системні параметри** і повторіть. |
| Вебхук не надходить | Три типові причини: адреса Odoo недоступна з інтернету, cron WordPress вимкнений (`DISABLE_WP_CRON`) і сайт без трафіку, або вебхуки не були зареєстровані. Замовлення все одно надходять через опитування кожні 10 хвилин. |
| `401 invalid signature` у логу вебхуків WordPress | Секрет вебхука у WordPress відрізняється від **секрету вебхука** магазину — типово це вебхук, створений вручну. Видаліть його і натисніть **Зареєструвати вебхуки** ще раз. |
| Попередження `Odoo total … differs from WooCommerce total …` | Жоден податок Odoo не має ставки податку WooCommerce, єдиний податок Odoo з такою ставкою включено в ціну, задіяно складну (compound) ставку, або купон зменшив доставку чи доплати. Перевірте **Журнал активності** й карту податків. |
| `No Odoo sale tax found for rate …` у серверному лозі Odoo | Створіть податок продажу з таким відсотком для компанії магазину, інакше замовлення імпортується без нього. |
| `The store URL cannot be changed after records have been synchronised` | URL є частиною ідентичності кожної відповідності. Створіть другий запис магазину. |
| Завдання залишаються **У черзі** | Планова дія черги неактивна або не працює жоден планувальник Odoo. Увімкніть **WooCommerce: process the synchronisation queue** і перевірте лог Odoo. |
| Завдання падають із `WooError` | Прочитайте **Останню помилку** завдання й відповідний рядок помилки в **Журналі активності**: там зберігаються HTTP-статус і код помилки WooCommerce. |
| Зображення не експортуються | У магазині відсутні або неправильні *Користувач WordPress* і *Пароль застосунку WordPress*. Про це каже попередження в журналі; товар усе одно експортується. |
| Повернення пропущено | Замовлення ще не імпортоване, або його замовлення продажу не має проведеного рахунку. Обидва випадки журналюються з причиною. |
| Залишки не надсилаються | Джерело запасів не **Odoo**, планова дія вимкнена (вона вимкнена після встановлення) або жоден товар не зіставлений. Скористайтеся **Синхронізувати зараз**. |

## 24. Політика підтримки

Це спільнотний проєкт, який підтримується за принципом найкращих зусиль:

* **платної підтримки немає**, гарантованого часу відповіді немає;
* підтримувані версії Odoo: **19.0 і 20.0**;
* звіти про помилки та pull request'и вітаються в трекері;
* вказуйте версію конектора (1.0.0), версію Odoo, версію WooCommerce, кроки
  відтворення проблеми й відповідні рядки **Журналу активності** з HTTP-статусом і
  кодом помилки WooCommerce.

Питання щодо самого Odoo або самого WooCommerce належать до їхніх каналів
підтримки.
