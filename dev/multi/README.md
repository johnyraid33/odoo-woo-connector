# dev/multi — second, independent WooCommerce store

A **second, fully independent** WooCommerce store for multi-store tests of the
`rex_woocommerce_connector` Odoo module.

The main verification stack in [`dev/`](../README.md) stays exactly as it
is (WordPress 7.1 / WooCommerce 11.2.2 / Odoo 20). This stack exists so the
connector can be tested

* against **two stores at the same time**, with disjoint SKUs and different data, and
* against an **older WooCommerce line** — **8.9.1** instead of the current 11.x.

Nothing in this directory is required to run the main stack, and the main stack
is never modified: this stack only **joins** its docker network.

---

## What is actually installed

| Component | Version / image | Notes |
| --- | --- | --- |
| WordPress | **6.5.5** (`wordpress:6.5.5-php8.3-apache`) | Pinned on purpose: WooCommerce 8.9.1 was released for the WP 6.5 line. The image is PHP 8.3 as requested, but the core is NOT the newest one. |
| WooCommerce | **8.9.1** | Downloaded from `https://downloads.wordpress.org/plugin/woocommerce.8.9.1.zip` (the newest 8.9.x release). |
| PHP | 8.3.9 | from the WordPress image |
| MySQL | **8.0.46** (`mysql:8.0`) | separate data volume |
| PostgreSQL | 17 (`postgres:17`) | parity with the main stack only — **no Odoo container here** |

There is deliberately **no Odoo container** in this stack: the connector under
test runs in the main stack's Odoo container and talks to this store over the
docker network.

## Services, aliases and ports

Compose project name: **`odoo-woo-connector-multi`**.

| Service | Container | Aliases / DNS | Host ports (loopback unless noted) |
| --- | --- | --- | --- |
| `wordpress-multi` | `odoo-woo-connector-multi-wordpress-multi-1` | `wordpress-multi` (on the **main** network too), `odoo-woo-connector-multi-wordpress-multi-1`, `localhost` (cert SAN only) | **8093** → 80 (all interfaces), **127.0.0.1:8444** → 443 |
| `mysql-multi` | `odoo-woo-connector-multi-mysql-multi-1` | `mysql-multi` | **127.0.0.1:3308** → 3306 |
| `pg-multi` | `odoo-woo-connector-multi-pg-multi-1` | `pg-multi` | **127.0.0.1:5434** → 5432 |
| `wpcli-multi` | `odoo-woo-connector-multi-wpcli-multi-1` | `wpcli-multi` | — (automation only, kept alive with `tail -f /dev/null`) |

Network wiring:

* `odoo-woo-connector-multi_default` — the stack's own private network;
* **`odoo-woo-connector-dev_default`** — the MAIN stack's network, joined as an
  *external* network. The WordPress container is attached to it with the alias
  **`wordpress-multi`**, which is why the main stack's Odoo container can call
  `https://wordpress-multi` directly.

> **Gotcha that cost one debugging round:** do not call these services `db` /
> `odoo-db`. The main stack already has services with exactly those names on
> `odoo-woo-connector-dev_default`, and Docker's embedded DNS merges names from
> every network a container is attached to — the multi WordPress container then
> resolved `db` to the **main** stack's MySQL and started serving the main store
> instead of its own. Every service here therefore carries a unique `-multi` suffix,
> and `WORDPRESS_DB_HOST` is set to the explicit `mysql-multi:3306`.

### TLS certificate

`certs/server.crt` / `certs/server.key` are generated by
`scripts/gen-cert.sh` (wired into `./multi.sh up`), self-signed, 825 days,
CN=`wordpress-multi`, with SAN:

```
DNS:localhost, IP:127.0.0.1, DNS:wordpress-multi, DNS:odoo-woo-connector-multi-wordpress-multi-1
```

HTTPS is required: WooCommerce performs HTTP Basic authentication only for SSL
requests, so authenticated REST calls over plain HTTP always answer **401**.
Delete `certs/` and run `./multi.sh up` to regenerate it.

## Credentials and the connector configuration

File: **`dev/multi/.woo_credentials.json`** (mode 600, git-ignored):

```json
{
    "base_url": "https://wordpress-multi",
    "host_base_url": "https://localhost:8444",
    "consumer_key": "ck_e016f30abfc0823fbe34ca6d78d77204cd4a31c2",
    "consumer_secret": "cs_...",
    "woo_version": "8.9.1",
    "generated_at": "2026-11-07T15:32:57+00:00"
}
```

* `base_url` — the address the **connector** must use (from the main stack's
  Odoo container).
* `host_base_url` — the same store as seen **from the workstation** (loopback
  HTTPS port); use this one for host-side `curl` / scripts.

What to put into Odoo (**WooCommerce → Configuration → Stores**):

| Field | Value |
| --- | --- |
| Store URL / `base_url` | **`https://wordpress-multi`** |
| Consumer key | from the file |
| Consumer secret | from the file |
| Verify the TLS certificate | **unchecked** (`verify_ssl = False`) |

Two things to be aware of:

1. **`https://wordpress-multi` is a container-network name.** It resolves only
   inside containers attached to `odoo-woo-connector-dev_default`. From the
   **host** the same store is `https://localhost:8444` (and `http://localhost:8093`
   for the browser/admin). Do not use `https://localhost:8444` in Odoo — the
   container cannot reach a loopback-published port.
2. **TLS verification must be disabled for this store**, because the certificate
   is self-signed and the main stack's Odoo container only trusts
   `/mnt/dev-certs/server.crt` (the main store's certificate). Setting
   `REQUESTS_CA_BUNDLE` to a bundle containing both certificates would also work,
   but that would mean changing the main stack — out of scope here. The module
   already has the `verify_ssl` switch for exactly this case.

WordPress admin: `http://localhost:8093/wp-admin/` — **admin / admin**
(`admin@example.com`). Not needed for REST, only for the UI.

## Usage

```bash
cd dev/multi

./multi.sh up          # start (needs the MAIN stack's network to exist)
./multi.sh seed        # install WP 6.5.5 + WooCommerce 8.9.1, seed data, issue REST key
./multi.sh verify      # full proof: authenticated REST from host AND from the main Odoo container
./multi.sh status      # containers, versions, HTTP codes, seeded counts, credentials summary
./multi.sh creds       # re-check / rotate the API key (--force = new key pair)
./multi.sh down        # stop, keep volumes
./multi.sh reset -y    # destroy volumes, start, seed from scratch
./multi.sh logs [svc]  # follow logs (wordpress-multi, mysql-multi, wpcli-multi, pg-multi)
```

`./multi.sh up` requires the network of the main stack, so start it first:

```bash
cd dev && ./dev.sh up     # or docker compose up -d in dev/
cd multi && ./multi.sh up
```

`seed` is idempotent: re-running it updates the same products, customers,
orders and refund instead of duplicating them (state is tracked in the
`woo_connector_multi_seed` option and matched by SKU/email).

## The curl proof (what was actually run)

### 1. Authenticated REST from the host — HTTP 200 + seeded products

```bash
cd dev/multi
KEY=$(grep -o '"consumer_key"[^,]*' .woo_credentials.json | sed 's/.*: *"//; s/"$//')
SECRET=$(grep -o '"consumer_secret"[^,]*' .woo_credentials.json | sed 's/.*: *"//; s/"$//')

curl -sk -u "$KEY:$SECRET" "https://localhost:8444/wp-json/wc/v3/products?per_page=100"
```

Result (HTTP 200, trimmed):

```
10 simple   MULTI-TSHIRT  | Multi Basic T-Shirt   | 12.00
11 simple   MULTI-MUG     | Multi Ceramic Mug     |  7.00
12 simple   MULTI-STICKER | Multi Sticker Pack    |  3.20
13 variable MULTI-HOODIE  | Multi Variable Hoodie | 39.00 | variations: [14, 15]
```

```
$ curl -sk -u "$KEY:$SECRET" https://localhost:8444/wp-json/wc/v3/orders/16/refunds?per_page=100
18 | amount: 5.00 | reason: Multi-store partial refund: 5.00 EUR for a damaged mug

$ curl -sk -u "$KEY:$SECRET" https://localhost:8444/wp-json/wc/v3/system_status | ...
wc_version: 8.9.1 | wp_version: 6.5.5 | php: 8.3.9 | mysql: 8.0.46
```

Unauthenticated calls behave as expected: `GET /wp-json/wc/v3/products` over
HTTPS **and** over HTTP returns **401** (WooCommerce rejects Basic auth without
a key; and over plain HTTP it does not even accept the key).

### 2. From the MAIN stack's Odoo container — the address the connector uses

```bash
$ docker exec odoo-woo-connector-dev-odoo-1 python3 -c \
    "import requests; r=requests.get('https://wordpress-multi/wp-json/', verify=False, timeout=15); print(r.status_code)"
200
```

With authentication (same command the module's client performs):

```bash
$ docker exec -i odoo-woo-connector-dev-odoo-1 python3 - <<'PY'
import requests, urllib3
urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)
base = "https://wordpress-multi"
print("GET /wp-json/ ->", requests.get(base + "/wp-json/", verify=False, timeout=20).status_code)
r = requests.get(base + "/wp-json/wc/v3/products", auth=(KEY, SECRET), verify=False, timeout=30)
print("GET /wp-json/wc/v3/products ->", r.status_code, [p["sku"] for p in r.json()])
PY
```

Actual output:

```
GET https://wordpress-multi/wp-json/ -> 200
GET https://wordpress-multi/wp-json/wc/v3/products (Basic auth) -> 200
SKUs: MULTI-HOODIE, MULTI-MUG, MULTI-STICKER, MULTI-TSHIRT
GET https://wordpress-multi/wp-json/wc/v3/orders (Basic auth) -> 200
orders: #17(processing), #16(completed)
```

And, for completeness, `verify=True` **fails** from the Odoo container
(expected — the multi certificate is not in the Odoo container's CA bundle):

```

VERIFY_FALSE status: 200
```

Everything above is automated in:

```bash
cd dev/multi && ./multi.sh verify
# ==> Verification PASSED
```

## Reset / troubleshooting

* Full wipe and re-seed: `./multi.sh reset -y`.
* The stack refuses to start when the main stack's network is missing:
  start `dev/` first (`cd dev && ./dev.sh up`).
* Host ports are overridable in `dev/multi/.env` (`WP_PORT`, `WP_HTTPS_PORT`,
  `MYSQL_PORT`, `PG_PORT`).
* "The site you have requested is not installed" from `wp`: WordPress is not
  installed yet — run `./multi.sh seed`. If it happens *after* a seed, check that
  `WORDPRESS_DB_HOST` still points at `mysql-multi:3306` and that no other
  service in this stack is called `db`.
* Seeding logs `sendmail: can't connect to remote host (127.0.0.1)` a few times:
  WooCommerce tries to send the "new order" e-mails and there is no MTA in the
  container. Harmless.
* The front-end over `https://localhost:8444/` 301-redirects to
  `https://localhost:8093/` (WordPress canonical redirect, because the site URL is
  the HTTP one). REST endpoints (`/wp-json/...`) are **not** redirected —
  that is why the connector's `base_url` can be `https://wordpress-multi` while the
  browser uses the HTTP port.
